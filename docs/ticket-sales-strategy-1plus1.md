# Atlas: стратегия продажи «1+1»

## Статус документа

Этот документ является обязательным техническим контрактом для реализации стратегии продажи `BUY_ONE_GET_ONE` в Atlas.

Стратегия продажи не заменяет тип билета и не меняет существующий дизайн создания категории. Она является отдельным слоем рядом со стратегией цены.

## Основной принцип

Организатор продает один комплект, покупатель оплачивает один комплект, но Atlas создает два самостоятельных допуска на мероприятие.

Для одного купленного комплекта система обязана:

- списать 2 единицы физической вместимости категории;
- зарезервировать 2 единицы вместимости до завершения оплаты;
- создать 2 отдельные записи `Ticket`;
- создать 2 разных QR-кода;
- создать 2 независимых Apple Wallet pass;
- разрешить два независимых прохода через сканер;
- показывать в заказе один комплект и два билета;
- при полном возврате отменить оба билета и вернуть 2 единицы вместимости.

## Модель данных

### TicketCategory

Добавляется поле:

```prisma
enum SalesStrategy {
  STANDARD
  BUY_ONE_GET_ONE
}

salesStrategy SalesStrategy @default(STANDARD)
```

`priceMinor` для `BUY_ONE_GET_ONE` является ценой одного комплекта из двух билетов.

`capacity` и `sold` всегда означают физическое количество допусков, а не количество комплектов.

### OrderItem

Заказ должен хранить снимок условий продажи, чтобы последующее изменение категории организатором не меняло уже созданный заказ.

Добавляются поля:

```prisma
salesStrategy SalesStrategy @default(STANDARD)
salesUnitQuantity Int @default(1)
admissionQuantity Int @default(1)
lineTotalMinor Int
```

Правила:

- `salesUnitQuantity` - количество купленных комплектов;
- `admissionQuantity` - количество физических билетов;
- для обычной продажи оба значения равны;
- для `BUY_ONE_GET_ONE`: `admissionQuantity = salesUnitQuantity * 2`;
- `lineTotalMinor = salesUnitQuantity * unitPriceMinor`;
- `unitPriceMinor` - цена одного комплекта, без деления на два.

Существующее поле `quantity` должно быть мигрировано или сохранено как совместимое поле только после проверки всех отчетов. Новая бизнес-логика не должна использовать неоднозначное значение `quantity`.

## Настройка организатором

В существующей форме категории, без изменения общего дизайна, добавляется поле «Стратегия продажи»:

- Обычная продажа;
- Билет 1+1.

При выборе «Билет 1+1» интерфейс поясняет:

- указанная цена является ценой за два билета;
- один выбранный комплект уменьшает остаток на два места;
- покупатель получает два отдельных QR-кода.

`maxPerOrder` для этой стратегии означает максимальное количество комплектов в одном заказе. В интерфейсе подпись должна автоматически меняться на «Максимум комплектов в заказе».

Нельзя включить `BUY_ONE_GET_ONE`, если:

- остаток категории меньше двух;
- категория уже имеет оплаченные заказы, созданные по другой стратегии;
- категория назначена объекту, продаваемому целиком, если число и цена допусков не определяются однозначно.

## Публичная карточка билета

Существующая карточка сохраняется. Меняется только содержание:

- название стратегии: `1+1`;
- цена: `199 ₪ за 2 билета`;
- счетчик означает количество комплектов;
- рядом с итогом показывается физическое количество билетов.

Пример:

- выбрано: 2 комплекта;
- покупатель получит: 4 билета;
- стоимость: `2 × 199 ₪`.

## Checkout API

Маршрут: `POST /api/checkout`.

Сервер обязан самостоятельно получить стратегию из базы. Клиент не является источником истины для множителя.

### Свободная рассадка

Для входного `quantity = N`:

- `salesUnitQuantity = N`;
- `admissionQuantity = N * 2`;
- проверка `minPerOrder` и `maxPerOrder` выполняется по комплектам;
- проверка вместимости и резервирование выполняются по физическим билетам;
- сумма выполняется по комплектам.

### Выбор конкретных мест

Покупатель выбирает физические места.

Для `BUY_ONE_GET_ONE`:

- количество выбранных мест должно быть четным;
- `salesUnitQuantity = seatIds.length / 2`;
- `admissionQuantity = seatIds.length`;
- каждое место резервируется отдельно;
- стоимость равна количеству пар, умноженному на цену комплекта;
- каждый созданный билет должен быть связан со своим местом через снимок заказа.

При нечетном количестве мест checkout возвращает понятную ошибку: «Для билета 1+1 выберите места парами».

### Объекты, продаваемые целиком

`BUY_ONE_GET_ONE` не применяется к `WHOLE_TABLE` в первой версии. Checkout должен отклонять такую комбинацию. Это исключает неоднозначность между ценой комплекта и ценой целого объекта.

### Промоутерские ссылки

- `guestLimit` считается в физических допусках;
- `maxPerOrder` ссылки считается в комплектах для `BUY_ONE_GET_ONE`;
- `customPriceMinor` считается ценой комплекта;
- квота уменьшается на `admissionQuantity`.

### Промокоды и комиссии

Порядок расчета:

1. Сумма комплектов.
2. Скидка промокода.
3. Сервисный сбор.
4. Итог покупателя.

Комиссия не должна рассчитываться от удвоенного числа физических билетов.

### Идемпотентность

Повторный запрос с тем же `idempotencyKey` не создает дополнительные резервы, билеты или платежи. Он возвращает существующий заказ.

## Резервирование и остатки

Маршруты и функции:

- `assertInventoryAvailable`;
- `createReservation`;
- подтверждение резерва после оплаты;
- освобождение истекшего резерва;
- отмена и возврат.

Во все эти процессы передается `admissionQuantity`, а не количество комплектов.

Инвариант категории:

```text
available = capacity - sold - activeReservedAdmissions
```

Для одного комплекта `BUY_ONE_GET_ONE` значение `activeReservedAdmissions` увеличивается на 2.

При успешной оплате `sold` увеличивается на 2.

При истечении неоплаченного заказа освобождаются 2 зарезервированных допуска.

## Оплата HYP

В HYP передается только итоговая сумма заказа. Количество физических билетов не должно повторно влиять на сумму.

Маршруты:

- создание ссылки оплаты;
- callback успешной оплаты;
- ручная оплата одобренного заказа;
- повторный запуск оплаты.

Все маршруты должны использовать сохраненный `Order.totalMinor` и не пересчитывать сумму как `quantity * unitPriceMinor` без учета `salesUnitQuantity`.

## Выпуск билетов

Функция: `issueTicketsForOrder`.

Количество создаваемых записей `Ticket` равно сумме `OrderItem.admissionQuantity`.

Для одного комплекта создаются два билета:

- разные `publicCode`;
- отдельный статус;
- отдельный Wallet serial;
- независимая история сканирования;
- общий `orderId`;
- общая категория.

Повторный вызов выпуска билетов не должен создавать дубликаты.

## Email, страница заказа и повторная отправка

Все представления заказа должны различать:

- количество комплектов;
- количество полученных билетов;
- итоговую стоимость.

Письмо содержит две отдельные ссылки или два отдельных вложения билетов.

Повторная отправка заказа отправляет оба билета.

Страница заказа отображает оба QR-кода отдельно.

## Apple Wallet

Wallet работает на уровне записи `Ticket`. Для заказа 1+1 создаются два независимых pass.

Обновление даты, места проведения, отмена заказа и другие push-обновления применяются к обоим билетам заказа.

## Сканер и check-in

Изменение протокола сканера не требуется.

Каждый QR проверяется независимо:

- первый билет может иметь статус `USED`;
- второй билет остается `VALID`;
- повторное сканирование первого возвращает `USED`;
- сканирование второго после этого возвращает `VALID`.

Сканер не должен пропускать двух людей по одному QR-коду.

## Одобрение заказа

Для мероприятий с `APPROVAL_REQUIRED` резервируется полное физическое количество билетов.

После одобрения сумма и количество комплектов не пересчитываются. После оплаты выпускается `admissionQuantity` билетов.

При отклонении освобождается полное физическое количество.

## Возвраты и отмены

### Полный возврат

- отменяется заказ;
- отменяются оба билета;
- Wallet получает обновление обоих pass;
- освобождаются 2 физических места на комплект;
- покупателю возвращается оплаченная сумма комплекта по правилам комиссии.

### Частичный возврат

В первой версии частичный возврат одного билета из комплекта запрещен.

Причина: покупатель приобрел неделимый коммерческий комплект. Разрешен возврат только целого комплекта, то есть двух связанных допусков.

Для будущей поддержки частичных возвратов потребуется отдельная сущность `OrderItemUnit` или `TicketBundle`.

## Отчеты и аналитика

Отчеты должны показывать отдельно:

- продано комплектов;
- выдано физических билетов;
- выручка;
- средняя цена комплекта;
- фактическая посещаемость по билетам.

Нельзя использовать количество строк `OrderItem` или `salesUnitQuantity` как посещаемость.

## Клонирование мероприятия

При клонировании категории копируется `salesStrategy`.

Счетчики `sold`, резервы, заказы и билеты не копируются.

## Обязательные тесты

1. Один комплект создает заказ на цену одного комплекта и два билета.
2. Два комплекта создают четыре билета.
3. Остаток 1 блокирует покупку комплекта.
4. Резерв одного комплекта блокирует 2 места.
5. Истечение оплаты возвращает 2 места.
6. Повторный checkout с тем же ключом не создает второй резерв.
7. Успешный callback HYP увеличивает `sold` на 2.
8. Повторный callback HYP не увеличивает `sold` повторно.
9. Два QR-кода проходят независимо.
10. Один QR нельзя использовать дважды.
11. Полный возврат отменяет оба билета и возвращает 2 места.
12. Частичный возврат одного билета блокируется.
13. Промокод применяется к цене комплекта один раз.
14. Комиссия считается от оплаченной суммы, а не от двух билетов.
15. Для карты нельзя выбрать нечетное количество мест.
16. Два выбранных места резервируются и создают два отдельных билета.
17. `WHOLE_TABLE` с `BUY_ONE_GET_ONE` отклоняется.
18. Клонирование копирует стратегию без продаж.
19. Изменение стратегии категории не меняет снимок существующего заказа.
20. Email, страница заказа и Wallet содержат два билета.

## Критерий готовности

Функция считается готовой только после прохождения всех тестов и ручной проверки полного маршрута:

```text
настройка категории -> публичная покупка -> резерв 2 мест -> HYP -> paid -> 2 Ticket -> 2 QR -> два независимых check-in -> полный возврат
```
